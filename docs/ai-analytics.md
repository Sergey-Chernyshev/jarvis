# Аналитика работы с ИИ в Jarvis

Jarvis читает трейсы Claude Code, Codex из локальных профилей и подключённых узлов
единого формата JSONL, сопоставляет наблюдаемые
правки с Git и позволяет записывать результаты задач. Экран помогает находить
проблемы в инструментах и харнесе, сравнивать модели и считать экономический
эффект на собственных данных.

Это три разных источника: события агента, изменения репозитория и подтверждённые
человеком результаты. Они не превращаются в единый рейтинг программиста.
Отсутствующие данные обозначаются как неизвестные.

Исследование индустрии, альтернативы, лицензии и первоисточники:
[как измеряют AI coding](ai-analytics-research.md). Этот документ описывает
именно реализованное поведение, а исследование также содержит дальнейшие идеи.
Настройка под другого пользователя, аккаунты и агенты:
[источники, правила и единый формат](ai-analytics-integrations.md).

## Как открыть и начать

1. Открой Jarvis → **Аналитика ИИ** (раздел с клавишей `3`).
2. Выбери период и, при необходимости, проект. Нажми **Обновить** после новых
   событий. Анализ запускается по запросу в отдельном рабочем потоке.
3. Посмотри покрытие: сколько файлов прочитано, были ли ограничения или ошибки.
4. Раскрой сессию: там есть измерения харнеса, ошибки инструментов, сигналы
   промптов, проверки результата и технические основания.
5. В разделе экономического эффекта раскрой **Записать результат задачи**:
   укажи тип задачи, точный ID модели, версию харнеса, результат и известные затраты.
6. Прежняя статистика токенов, биллинга и подписочных лимитов доступна через
   **Расход и лимиты**. Она использует прежний источник `usage`, её оценочная
   стоимость по API не подставляется в фактическую экономику задач.

Настраивать ключи или платить за модель-оценщика не нужно. Jarvis не отправляет
тексты в LLM для оценки. Список доступных проектов появляется из прочитанных
трейсов; если данных нет, запусти Claude/Codex и проверь доступность их журналов.
Для собственных источников открой **Настройки аналитики**. Там настраиваются
пути, формат событий, включение автообнаружения, лимиты и правила; параметры
экономики можно задать по умолчанию для своего профиля.

## Что показывается

| Показатель | Источник и смысл | Чего он не доказывает |
| --- | --- | --- |
| Запросы пользователя | Реальные пользовательские сообщения, без известных служебных вставок и результатов инструментов | Количество законченных задач |
| Вызовы инструментов | Уникальные наблюдаемые call ID, имена, статусы, повторы | Что каждый вызов был нужен |
| Успех / ошибка / неизвестно | Статус результата, сопоставленного с вызовом | Семантическую правильность результата |
| p50 / p95 инструментов | Время между вызовом и подтверждённым завершением с корректными timestamp | Полное время человека или сервиса за пределами захвата |
| Активность агентов | Сумма интервалов событий, каждый ограничен настраиваемым пределом (по умолчанию пять минут) | Рабочие часы человека и экономию времени |
| Интервал наблюдения | От первого до последнего события выбранных сессий | Время непрерывной работы |
| Токены по модели | Наблюдаемые usage-записи, кэш отдельно | Сумму счёта за подписку |
| Совпадения правок ИИ | Сопоставление добавленных строк текущего дерева с успешными редактированиями | Доказанное авторство всего репозитория |
| Авторство Git AI | Метаданные установленного Git AI для добавлений последнего коммита | Полноту захвата всех редакторов и агентов |
| Расчётный эффект | Введённое время, ручная база сравнения, ставка и реальные затраты | Причинно доказанную экономию или прибыль на банковском счёте |

### Период и область данных

**Сегодня** — с местной полуночи; **7 дней** и **30 дней** — скользящие интервалы;
**всё** — доступная история в пределах лимитов чтения.

Период выбирает **сессии с последней наблюдаемой активностью в этом интервале**.
Метрики выбранной сессии считаются целиком: это сохраняет пары вызов–результат и
базу накопительных токенов. Поэтому длинная сессия может добавить события более
раннего периода. Это не отчёт о строго почасовом расходе; для него есть прежний
экран usage. Сессия без timestamp не попадает в ограниченный период.

Git показывает **состояние рабочего дерева сейчас**, а Git AI — **добавления
HEAD**. Они не фильтруются периодом трейсов. Результаты задач выбираются по дате
последнего сохранения записи, отдельно от периода её сессии.

## Как оценивается харнес

Харнес — инструкции, контекст, доступные инструменты, управление работой и
проверки вокруг модели. Текущий score версии `operational-evidence-heuristic-v2`
измеряет только три наблюдаемые стороны процесса:

| Измерение | Формула, 0–100 |
| --- | --- |
| Успешные результаты инструментов | `100 × eligibleSuccess / (eligibleSuccess + eligibleErrors)` |
| Наблюдаемость результатов | `100 × (eligibleSuccess + eligibleErrors) / eligibleCalls` |
| Проверка после последнего редактирования | `100`, если последняя распознанная проверка началась после последней подтверждённой правки и завершилась успешно; иначе `0` |

Если знаменателя нет, значение — `null`, измерение не участвует в среднем.
`eligible` обозначает напрямую наблюдаемые инструменты. Непрозрачные оболочки
`exec`/`parallel` не участвуют в этих двух измерениях: успешное завершение
оболочки не означает успех её внутренних инструментов. Их статус и количество
показаны отдельно. У сессии только с такими оболочками score может быть неизвестен.
Например, без наблюдаемых редактирований проверка после правки неприменима.
По умолчанию score сессии — равновесное среднее доступных измерений. Веса можно
изменить или отключить отдельное измерение; тогда используется взвешенное среднее
применимых значений. Score экрана — среднее
по сессиям с оценкой. Число учтённых сессий и знаменатели доступны в интерфейсе.

**100 не означает, что код правильный, архитектура хорошая или харнес оптимален.**
Неизвестный результат снижает наблюдаемость, но не записывается как ошибка модели.
Ошибка ожидаемого теста в цикле разработки всё равно является наблюдаемым
неуспехом команды: причину нужно смотреть по задаче. Сравнивай score только при
похожих задачах, инструментах и полноте захвата.

Диагностика показывает ошибки, неоднозначные/отсутствующие результаты, повторные
аргументы, отсутствие наблюдаемой финальной проверки, непрозрачные оболочки
инструментов, повреждение или обрезку трейса. Основания содержат количества и
ограниченный список call ID, по которым можно найти событие в оригинальном JSONL.

Из явных событий извлекаются сжатия контекста, сбросы счётчиков токенов и, если
провайдер сообщает размер окна, наблюдаемое отношение входа к окну. По умолчанию порог 85%
даёт информационный сигнал: это повод проверить контекст, а не доказательство
его потери. Сброс счётчика также сам по себе не доказывает компакцию.

### Проверки результата

Распознаются известные простые команды тестирования/проверки (`cargo test/check`,
`pytest`, `node --test`, `go test`, соответствующие команды npm и другие
поддержанные формы). Подтверждение требует успешного результата инструмента.
Вызов, вывод справки или сбор тестов без запуска не считается прохождением теста.
Сложный shell с `||`, пайпами, фоновым запуском через `&` и произвольными программами
остаётся вне такой оценки: нулевой код shell может скрывать упавшую или ещё
выполняющуюся проверку.

Проверка должна начаться **после завершения последней подтверждённой правки**.
Более поздняя неуспешная/неизвестная проверка не позволяет опираться на старый pass.
Ревью требований, достаточность тестов и принятие пользователем этим не заменяются.

### Промптинг

По русским и английским словам показывается наличие четырёх признаков: цель,
контекст, ограничения, способ проверки. Для каждого указаны наблюдения и
знаменатель. Эти признаки **не включены в score харнеса** и не оценивают промпт по
длине. «Да, сделай» может быть достаточным продолжением хорошего диалога.

Используй признаки как подсказку для разбора неудачных задач: были ли названы
ожидаемый результат, важные файлы и ограничения, было ли понятно, как проверить
работу. Семантический score качества промпта не выдумывается; для такой оценки
нужны рубрика и подтверждённые результаты.

## Процент кода ИИ и человека

### Без дополнительных инструментов

Jarvis извлекает текст только из **подтверждённых успешных** `Edit`, `Write` и
`apply_patch`, затем ищет точные совпадения добавленных строк в том же файле
текущего рабочего дерева. Неуспешные или неизвестные записи не дают атрибуции.
Повторные экземпляры одинакового текста ограничиваются количеством наблюдений;
строки короче 12 непробельных символов по умолчанию не атрибутируются из-за
неоднозначности. Фильтры файлов и минимальная длина настраиваются.

Знаменатель — добавленные строки изменённых и новых исходников. Удаления
показываются отдельно. По умолчанию исключаются зависимости, каталоги сборки, lockfiles,
минифицированные и известные сгенерированные файлы; документация и конфигурация
не входят в список расширений исходников. Файлы переименования рассматриваются
как удаление и добавление. Изменения могут принадлежать нескольким сессиям.

```text
доля совпадений = 100 × совпавшие добавленные строки / все добавленные строки исходников
неизвестно = все добавленные строки − совпавшие
ручное авторство = неизвестно (null)
```

Это **совпадения с правками ИИ, а не доказанное авторство**. Например, человек мог
повторно написать текст из старого AI-изменения, или AI-код мог быть переработан
вручную. Совпадения не отслеживают происхождение через историю Git, не измеряют
долю всех строк репозитория и не превращают остаток в «написано человеком».

### Если Git AI уже установлен

Jarvis запускает локальную команду `git-ai stats HEAD --json`. Он не устанавливает
Git AI, не добавляет хуки, не изменяет Git-конфигурацию и не делает fetch/push.

Используются `ai_additions`, `human_additions`, `unknown_additions` и
`git_diff_added_lines`. Их сумма проверяется перед показом процентов. Старый
формат без `unknown_additions` не трактуется как подтверждённое ручное авторство.
Нулевой знаменатель даёт неизвестный процент. Эти цифры описывают добавления
**последнего коммита**, с фильтрами Git AI, отдельно от текущего diff Jarvis.

Для устойчивой атрибуции новых правок можно самостоятельно настроить
[Git AI](https://github.com/git-ai-project/git-ai). Начать захват сейчас не значит
восстановить достоверное авторство старой истории. Поддержка Entire, импорт
произвольных OTLP-трейсов и перехват ручного ввода в редакторе пока не реализованы.

## Время, затраты и профит

Нельзя восстановить ручное рабочее время по timestamp агента. В форме результата
записываются отдельно:

- тип задачи и сессия;
- модель/состав моделей и версия харнеса для сопоставимых групп;
- принято, нужна переделка или отклонено;
- время выполнения без ИИ и его источник: измерение или оценка;
- активное время человека с ИИ, включая постановку задачи, без ревью/переделок;
- время ревью и переделок отдельно;
- стоимость часа и фактические затраты на ИИ в одной валюте;
- основание принятия, например тесты и ревью.

Пропущенное поле — неизвестно; явный ноль — известное отсутствие затрат.
Фактическая стоимость может быть суммой API-счёта или явно распределённой долей
подписки. Распределяй подписку последовательно, не учитывай один расход дважды.
Результат — ручная запись: Jarvis не проверяет банковские счета или истинность
указанных часов.

Для принятой задачи:

```text
T = минуты работы с ИИ + ревью + переделки
B = минуты выполнения без ИИ
экономия минут = B − T
стоимость времени = T / 60 × ставка
эффект = (B − T) / 60 × ставка − фактические затраты на ИИ
ускорение = B / T
ROI полных затрат = 100 × эффект / (стоимость времени + затраты на ИИ)
```

Для отклонённого результата или задачи, которая ещё требует переделки, выгода
не начисляется (`B = 0`), а известные затраты учитываются. После принятия обнови
запись с окончательными часами. Нулевой знаменатель даёт `null`; отрицательные
значения сохраняются. Разные валюты не складываются и не конвертируются.

Например, вручную задача занимала 120 минут, с ИИ — 30 минут работы, 15 минут
ревью и 15 минут переделок. При ставке $60/ч и затратах $10: экономия 60 минут,
эффект $50, ускорение 2×, ROI полных затрат около 71,4% (`50 / 70`). Это денежный
эквивалент высвободившегося времени, **не дополнительные $50 на счёте**.

Групповой эффект включает только записи с полными необходимыми данными, с
показом числа исключённых записей. Все известные расходы дополнительно показаны
отдельно, включая неполные записи. Повторное сохранение результата той же сессии
и типа задачи обновляет запись; отдельные задачи одного типа внутри одной сессии
нужно учитывать суммарно, чтобы не удваивать выгоду.

## Подходит ли выбранная модель

Трейсы показывают точные наблюдаемые ID моделей, запросы, токены и статусы
инструментов. Эти данные сами по себе не выбирают лучшую модель.

Записанные результаты группируются по **проекту, типу задачи, модели, версии
харнеса и валюте**. Выводятся приёмка, среднее время с ревью и переделками,
затраты на принятый результат. Последняя метрика включает затраты на неудачные
попытки в числителе. Если часть времени/затрат неизвестна, соответствующая метрика
не заполняется вместо подстановки нулей.

По умолчанию для сравнения нужны хотя бы пять записей с данными на вариант;
порог настраивается. Это минимальный
порог диагностики, а не статистическая гарантия. Если в той же группе другая
модель имеет не худшую приёмку, не большее время и затраты на принятый результат,
и строго лучше хотя бы один показатель, Jarvis предлагает её как **кандидата
для парного сравнения**. Автоматического переключения нет. Неравная сложность
задач, самоотбор и маленькие выборки могут объяснять отличие.

Фиксируй версию инструкций/настроек в поле харнеса, например Git SHA, и меняй один
фактор за раз. Для серьёзного решения прогони обе модели на одинаковом наборе
задач с одинаковой рубрикой приёмки, несколькими повторами и одинаковыми условиями.
Автоматические eval-прогоны и оценка DORA без CI/deploy/incident-данных пока отсутствуют.

## Источники, хранение и ограничения

- Claude: `~/.claude/projects/**.jsonl`, также `$CLAUDE_CONFIG_DIR/projects`.
- Codex: все включённые профили реестра `agent-instances.json`, их `sessions` и
  `archived_sessions`. Реестр объединяет стандартный `~/.codex`, `$CODEX_HOME`,
  безопасно обнаруженные `codex-*` wrappers и явно добавленные профили.
  Алиасы одного каталога не дублируются; личный и рабочий профили подписаны отдельно.
- Подключённые узлы `jarvis-node` protocol 2: `/sources` и `/sessions` объявляют
  доступные профили, а `/file` передаёт ограниченные части их трейсов через существующий
  SSH-туннель. Пути гостевой машины не открываются локально. Одноимённые проекты
  разных машин имеют разные ключи `remote://<machine>/<cwd>`; удалённый Git
  показывается как `not-inspected`, без притворной проверки локального репозитория.
- Старые ID результатов сохраняются: стандартный Codex — `codex:<sid>`, явно
  настроенные источники — `source:<id>:<sid>`. Дополнительные профили используют
  `source:<instanceId>:<sid>`, узлы — `source:remote:<machine>:<instanceId>:<sid>`.
- Дополнительные источники задаются в настройках: `claude`, `codex` или
  `normalized`, каталог или отдельный JSONL. Каждый источник имеет стабильный ID.
  Отключив автообнаружение, можно читать только выбранные источники.
- Обход ограничен 20 000 JSONL-файлами, 100 000 просмотренными записями каталогов и глубиной 8;
  по умолчанию за отчёт обрабатываются до 200 файлов,
  до 256 МиБ суммарно. Без фильтра это самые свежие файлы. При выборе проекта
  сначала приоритетно отбираются совпадения его cwd из ограниченного чтения
  заголовков (до 64 КиБ на файл / 16 МиБ суммарно), затем применяется точный
  фильтр разобранных сессий. Неизвестные заголовки не объявляются чужим проектом.
  Бюджеты файлов, байтов и числа проектов можно изменить в настройках.
  При больших архивах отчёт явно неполон; это не полный архивный backfill.
- Для узлов резервируется до четверти общего бюджета (полный бюджет при выборе
  удалённого проекта), максимум 8 узлов, 64 файла и 64 МиБ. Эти чтения учитываются
  в общем бюджете. Недоступные узлы, тайм-ауты и обрезанные трейсы видны в покрытии.
- Расход конкретного удалённого чата читается отдельно из его точного профиля и
  транскрипта: до 8 МиБ / 100 000 строк / 8 секунд. Он не запускает общий отчёт.
  Производные данные кэшируются в памяти; при отключении узла показываются как
  устаревшие, а отсутствие usage — как неизвестное значение, не нулевой расход.
  `/usage` Claude — квота отдельного профиля, она не подставляется вместо расхода чата.
- По умолчанию файл читается с начала, до 32 МиБ / 200 000 строк. Неполная последняя JSONL-строка
  не считается событием; повреждение и обрезка отражаются в покрытии.
- Канонические пути и ID сессий предотвращают двойной учёт алиасов. Claude usage
  объединяется по message ID, Codex — по дельтам накопительных счётчиков с
  защитой от повторов/сбросов. Reasoning входит в output и второй раз не суммируется.
- Запущенная фоновая команда без достоверно связанного финального результата
  остаётся неизвестной. Произвольный JavaScript внутри `functions.exec` не
  исполняется и не выдаётся за распознанные вложенные вызовы.
- Git: по умолчанию до 20 проектов за отчёт; команда ограничена 4 секундами и 8 МиБ вывода,
  patch — 500 путями/64 КиБ аргументов, новые файлы — 1 МиБ каждый и 8 МиБ всего.
  Недоступность и частичность показаны отдельно.
- Производный кэш трейсов и отчёта находится только в памяти процесса, отчёт
  переиспользуется до 30 секунд. **Обновить** обновляет отчёт; неизменные файлы
  переиспользуются по размеру и времени модификации. Перезапуск очищает кэш.
- Результаты задач лежат в `$JARVIS_DIR/analytics-outcomes.json` (по умолчанию
  `~/.jarvis/analytics-outcomes.json`), с правами `0600` и атомарной заменой.
  Порченый файл не перезаписывается пустым. Предел — 10 000 записей / 8 МиБ.
- Сырые промпты, аргументы инструментов и исходники не сохраняются в файл
  результатов и не входят в отчёт. Текст подтверждённых правок используется
  временно в памяти для сопоставления. В отчёте остаются локальные пути, ID,
  числа и диагностические основания; заметки о принятии — введённый пользователем текст.
- Кнопка копирования JSON копирует локальный отчёт. Перед передачей отчёта
  учитывай пути проектов и свои заметки; автоматической отправки нет.

## API и проверка реализации

Панель вызывает Tauri-команды `analytics_report` и `analytics_save_outcome`,
а настройки — `analytics_config_get`, `analytics_config_save`, `analytics_config_defaults`.
Для доступных потребителей capability/MCP зарегистрирован read-only инструмент
`analytics.query` с аргументами `period`, `project`, `refresh`. Его результат
помечен как untrusted, поскольку ID, названия моделей и заметки происходят из
внешних по отношению к агенту данных. Это данные, не инструкции.

Пример аргументов чтения:

```json
{"period":"week","project":"/absolute/path/to/repository","refresh":true}
```

Схема отчёта `schemaVersion: 1` содержит применённые `config` и `settingsHash`,
найденные `discoveredProjects`, `coverage`, `summary`, `sessions`,
`projects`, `models`, `outcomes`, `economics`, `limitations`. У каждого измерения
харнеса доступны `observed`, `total`, `score`, `explanation`. Формат исходных
трейсов внутренний и меняется; неподдержанный формат снижает наблюдаемость.

Код: `src-tauri/src/analytics/{mod,trace,repository,outcomes,config}.rs`,
`ui/ai-analytics.js`, `ui/ai-analytics.css`. Для проверки:

```bash
cargo test --offline --manifest-path src-tauri/Cargo.toml --bin jarvis analytics:: --no-default-features
npm run test:ui
```

Есть отдельный добровольный read-only smoke на локальных журналах:

```bash
cargo test --offline --manifest-path src-tauri/Cargo.toml --bin jarvis analytics::tests::local_machine_report_smoke --no-default-features -- --ignored --nocapture
```

Обычные тесты используют синтетические события и временные репозитории; они
проверяют дедупликацию, unknown, порядок проверок, лимиты, Git-настройки,
изолированное хранение и отсутствие сырого кода в отчёте.
