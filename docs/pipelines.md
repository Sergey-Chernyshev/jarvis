# Пайплайны: цикл как граф, BPMN и параллельные ветки

Цикл умеет крутить одну рутину: позвать агента → прогнать гейты → спросить
критика → повторить. Пайплайн — это тот же цикл, но собранный из разных шагов
со своими переходами: разведка, правка, тесты, ревью, вопрос человеку. И с
параллельными ветками, каждая в своём рабочем дереве.

Граф выгружается в **BPMN 2.0**, правится в **Camunda Modeler** и забирается
обратно без потерь.

## Зачем граф, если есть цикл

Цикл — один сценарий. Он честно закрывает «чини, пока не позеленеет» и
беспомощен, как только работа состоит из разных шагов: «сначала разведка
планом, потом правка, потом тесты, а если тесты красные — вернуться к правке с
их выводом». Такое в одну итерацию не укладывается, и попытка уложить
превращает конфигурацию цикла в смирительную рубашку.

Пайплайн отвечает на это ровно тем, чем отвечает BPMN: узлами и переходами.

## Из чего собирается

| узел | что делает |
| --- | --- |
| **агент** | зовёт агента с этим промтом |
| **команда** | выполняет команду; её код возврата и решает, куда идти дальше |
| **ревью** | второй агент читает дифф и отвечает вердиктом (`OK` / `RETURN` / `ASK`) |
| **человек** | прогон замирает и ждёт ответа из панели |
| **пауза** | ждёт чужую сборку или деплой |
| **развилка** | уходит РОВНО ОДИН переход — первый, чьё условие сошлось |
| **ветвление** | уходят ВСЕ ветки разом, каждая в своём `git worktree` |
| **слияние** | ждёт все ветки и сводит их рабочие деревья обратно |

И одно свойство поверх любого шага с работой — **«для каждого»**: выполнить его
по разу на элемент списка, каждый раз в своей ветке. Ветвление рисуют заранее, а
список бывает известен только на ходу.

Переход срабатывает по условию: *всегда*, *если получилось*, *если не вышло*,
*если вердикт …*, *если в выводе есть …* — или выражением, набранным в
модельере. **Первый подходящий переход и выигрывает**: порядок задаёт человек, и
«сработали оба» здесь означало бы недетерминированный прогон.

Результат узла виден следующим: `${тесты.вывод}`, `${тесты.код}`,
`${ревью.вердикт}`. Именно так «отдай правщику вывод тестов» и выражается.
Неизвестная переменная **остаётся текстом как есть** — молча подставленная
пустота даёт промт, из которого половина задачи испарилась незаметно.

## Параллельные ветки

```
                    ┌─→ фронт  (worktree проект-3-фронт, ветка loop/проект-3-фронт)  ─┐
план ─→ ⊕ ветвление ┤                                                                  ├─→ ⊕ слияние ─→ тесты
                    └─→ бэк    (worktree проект-3-бэк,   ветка loop/проект-3-бэк)    ─┘
```

Параллель здесь настоящая, и стоит она на одном условии: **у каждой ветки своё
рабочее дерево**. Два агента в одном каталоге затирают друг другу файлы —
«параллельно» без отдельных worktree было бы просто ложью. Поэтому:

* ветвление коммитит работу текущей дорожки и поднимает `git worktree` на своей
  ветке **от этого состояния** — то, что сделали шаги до ветвления, ветки видят;
* ветки идут одновременно, каждая своим каталогом и своей веткой git;
* слияние ждёт все входящие ветки, коммитит каждую и вливает честным
  `git merge --no-ff`;
* влитые рабочие места убираются, **ветки git остаются** — в них работа.

Вложенная параллель работает: ветка внутри ветки читается путём —
`проект-3-фронт-стили`.

### Для каждого элемента — своя ветка

Ветвление рисуют заранее, а список бывает известен только на ходу: «для каждого
упавшего теста», «для каждого файла из вывода». Для этого у **шага** есть поле
**«для каждого»** — выражение, дающее список по строке на элемент:

```
найти упавшие  (команда)   →  починить  (агент, для каждого: ${найти.вывод})  →  тесты
                                 ├─ ветка 1: ${элемент} = tests::alpha
                                 ├─ ветка 2: ${элемент} = tests::beta
                                 └─ ветка 3: ${элемент} = tests::gamma
```

Шаг выполняется столько раз, сколько строк в списке, каждый раз в **своём
worktree**; внутри шага элемент виден как `${элемент}` (или `${item}`). Когда
все закончили, ветки сливаются обратно тем же способом, что и у слияния, — и ход
идёт дальше одним токеном. Отдельного слияния рисовать не надо: ветвление и
сведение тут неявные, вокруг одного узла.

Это multi-instance из BPMN: в модельере такой шаг рисуется тремя полосками под
задачей, а список лежит в `camunda:collection`.

Мелочи, которые важны на практике:

* строка на элемент, пустые и повторы выбрасываются — два одинаковых элемента
  дали бы две ветки, правящие одно и то же, и гарантированный конфликт;
* потолок — **20 экземпляров**: двадцать worktree это уже гигабайты и двадцать
  агентов на один лимит аккаунта, а больше почти наверняка значит, что список
  получился не тот;
* **пустой список — не ошибка**: чинить нечего, шаг пропускается, и в журнале
  об этом есть строка (молча пропущенный шаг выглядит поломкой);
* если один экземпляр сорвался, остальные всё равно сливаются — сосед мог
  сделать работу, и выбрасывать её из-за чужой неудачи не за что. О неудаче
  скажет результат узла: `${шаг.код}` — сколько экземпляров сорвалось.

### Конфликт слияния

Правило конфликта — свойство узла, который сливает: слияния или шага «для
каждого». Умолчание — **остановиться**: молча выбрать сторону значит выбросить
чью-то ночь работы, не сказав об этом ни слова. Дерево при этом откатывается в рабочее
состояние: прогон, застрявший в незавершённом слиянии, не смог бы больше ничего.

| правило | что делает |
| --- | --- |
| `остановиться` | инцидент с именами конфликтных файлов |
| `отдать агенту` | агент разбирает конфликт прямо в дереве, где тот лежит |
| `оставить свою` / `взять чужую` | `-X ours` / `-X theirs`: сторона выбирается **внутри конфликтного участка**, остальные правки ветки приезжают всё равно |

«Отдать агенту» — единственное место, где агент трогает чужую работу, и промт
там запрещает самое соблазнительное: выбрать сторону целиком. Результату верим
не на слово — дерево проверяется на оставшиеся маркеры `<<<<<<<`, и коммит
делаем мы, а не он.

### Что параллель не делает

* **Вопрос человеку замораживает ВЕСЬ прогон**, а не одну ветку. Дать соседним
  веткам работать дальше, пока человек спит, значит получить к утру слияние с
  работой, о которой он ещё не высказался.
* **Ветвление без слияния — ошибка сборки**, и панель говорит об этом до
  запуска: разбежавшиеся ветки означают worktree'ы, которые никуда не вольются.
* **Слияние, до которого пришли не все ветки, — инцидент**, а не вечное
  ожидание. Прогон, выглядящий работающим и ничего не делающий, хуже упавшего.
* **Параллель требует отдельного рабочего дерева** (`worktree` в песочнице
  цикла). Без него это два агента в одном каталоге.

## BPMN: правка в Camunda Modeler

Конструктор в панели хорош на пяти узлах и беспомощен на двадцати пяти: списком
читается порядок, но не читается ФОРМА — где ветвление, куда возвращается петля,
что идёт параллельно. Нарисованный граф отвечает на это взглядом. Своё полотно
со стрелками писать незачем: bpmn-js уже написан, а Camunda Modeler бесплатен.

**Как пользоваться.** В конструкторе пайплайна, внизу — строка «BPMN»:

1. **Выгрузить в .bpmn** — файл ложится в `~/.jarvis/pipelines/<имя>-<id>.bpmn`
   и открывается тем, чем `.bpmn` открывается на этой машине.
2. Правишь в модельере: таскаешь узлы, дорисовываешь ветки, меняешь условия.
3. **Сохраняешь файл** — Jarvis подхватывает правку сам, как только панель
   обновится. Кнопка «Забрать из файла» делает это немедленно.
4. Правка в панели уезжает в файл сразу же, так что открытый модельер всегда
   показывает свежий граф.

Спор двух правок невозможен: у того, кто сохранил позже, время правки больше —
оно и решает. «Отвязать» разрывает связь с файлом.

### Как одно ложится на другое

| Jarvis | BPMN |
| --- | --- |
| агент, ревью | `bpmn:serviceTask` |
| команда | `bpmn:scriptTask` (+ `bpmn:script`) |
| человек | `bpmn:userTask` |
| пауза | `bpmn:intermediateCatchEvent` с таймером (`PT30M`) |
| развилка | `bpmn:exclusiveGateway` |
| ветвление, слияние | `bpmn:parallelGateway` |
| переход | `bpmn:sequenceFlow` + `bpmn:conditionExpression` |
| промт / команда / вопрос | `bpmn:documentation` |
| для каждого | `bpmn:multiInstanceLoopCharacteristics` + `camunda:collection` |
| модель, попытки, вид узла | `camunda:properties` |

**Промт лежит в `documentation`** не от бедности: это единственное поле, которое
модельер даёт править у любого элемента. Всё остальное — в
`camunda:properties`, которые он показывает таблицей.

Условия читаются и пишутся выражениями: `${ok}`, `${fail}`,
`${verdict == 'return'}`, `${contains(output, 'FAILED')}`, `${code != 0}`.

### Идентификаторы: почему в файле латиница

Схема XML разрешает в идентификаторе любые буквы, и кириллица там законна. На
практике — нет: bpmn-js и Camunda Modeler стоят на `moddle`, а он проверяет
идентификаторы своим ASCII-шаблоном и отвечает «illegal ID». Узел с русским
идентификатором не просто теряет имя — он **не разбирается целиком**, и полотно
открывается пустым, без единого слова о причине.

Поэтому в файл едет транслитерация (`тесты` → `testy`), а настоящий
идентификатор лежит рядом в `jarvis:id`. Обратное чтение берёт именно его, так
что `${тесты.вывод}` в чужих промтах продолжает работать.

### Проверка чужим парсером

Наши тесты проверяют, что мы читаем то, что сами написали, — и на этом вопросе
сходятся всегда. А открывается файл не нами. Отсюда отдельная проверка тем самым
парсером, на котором стоит модельер:

```bash
npm i --no-save bpmn-moddle
node scripts/check-bpmn.mjs ~/.jarvis/pipelines/ночной-loop-1.bpmn
node scripts/check-bpmn.mjs файл.bpmn --rewrite   # + переписать его модельером
```

Ноль предупреждений — файл откроется. `--rewrite` кладёт рядом версию,
переписанную самим `bpmn-moddle`: прочитать её обратно в панели и есть
настоящий круг через модельер. Такой слепок лежит в тестах
(`src-tauri/src/loops/testdata/camunda-rewritten.bpmn`) и читается на каждом
прогоне.

### Чего обмен не теряет

* **Расстановку.** Координаты узлов живут в модели: раскладка, сделанная руками,
  — работа человека, и автораскладка не имеет права её стирать. Своя раскладка
  считается ровно один раз, при первой выгрузке.
* **Идентификаторы.** `jarvis:id` едет в файл отдельным свойством, поэтому
  переименование узла в модельере **не ломает** `${узел.вывод}` в чужих промтах.
* **Чужие выражения.** Условие, которое мы не поняли (`${myBean.decide(…)}`),
  хранится текстом и возвращается в файл тем же текстом. Упростить чужую правку
  до ближайшей знакомой — значит молча её потерять. Такой переход **не
  срабатывает никогда** и объявляется в списке претензий: непонятое условие,
  тихо пропускающее ход, — худший вид поломки.
* **Порядок ветвей.** Переход по умолчанию Camunda (атрибут `default`) при
  чтении становится «всегда» и уезжает вниз списка: «всегда» посреди списка
  съело бы все условные ветки ниже.

### Файл, нарисованный с нуля

Обратное чтение принимает и то, чего мы никогда не писали: человек рисует в
модельере обычные задачи и шлюзы, ничего не зная про наши свойства. Такой узел
опознаётся по тегу BPMN, а идентификатор ему даётся **от имени** — чтобы
`${тесты.вывод}` заработало ровно так, как он и ожидал, увидев на схеме задачу
«тесты». Ромб с плюсом различается по форме графа: расходится — ветвление,
сходится — слияние.

## Прогон

Ход по графу — это **токен** в терминах BPMN, и их бывает несколько. Всё
остальное работает одинаково что для одного хода, что для пяти:

* **попытки**: узел, сорвавшийся из-за моргнувшей сети, повторяется сам и лишь
  исчерпав их зовёт человека;
* **инцидент**: идти некуда — прогон встаёт и говорит, на каком узле. Молча
  закончить «успешно» было бы худшим из исходов;
* **ограничители** цикла (токены, шаги, минуты) работают как обычно;
* **журнал**: каждый шаг — строка с именем узла и веткой, в которой он шёл. Без
  имени ветки журнал параллельного прогона нечитаем: три «правки» подряд, и
  непонятно, которая из них чья.

Живые ходы, их рабочие места и результаты шагов лежат **в запуске**, а не в
памяти движка: прогон переживает перезапуск приложения и вопрос человеку.

## Диагностика

| симптом | что смотреть |
| --- | --- |
| «ветви никуда не сходятся» | ветвление без слияния: ветки разбегутся, и их worktree никуда не вольются |
| «параллельные ветви требуют отдельного рабочего дерева» | включи `worktree` в песочнице цикла |
| «слияние: пришло 1 из 2 веток» | в одной ветке развилка увела ход мимо слияния — посмотри её условия |
| «„для каждого“ ждёт выражение со списком» | там должен стоять `${шаг.вывод}`, а не текст: список берётся из результата предыдущего шага |
| «для каждого» ничего не сделал | посмотри строку журнала: «список пуст» значит, что выражение дало пустой вывод |
| «условие … не разобрано» | выражение из модельера вне понятного языка; переход не сработает никогда |
| «до шага … никогда не дойдёт очередь» | узел недостижим — в выгруженном `.bpmn` он стоит отдельной колонкой справа |
| правка в Camunda не подхватилась | файл сохранён? связь видна строкой «BPMN»; кнопка «Забрать из файла» читает немедленно |
| «занят веткой …, а нужна …» | каталог дорожки занят чужой веткой: убери `~/.jarvis/worktrees/<имя>-<n>-*` |

Полезное на диске:

```bash
ls ~/.jarvis/worktrees/        # рабочие места запуска и его веток
ls ~/.jarvis/pipelines/        # файлы .bpmn
git -C <репозиторий> branch --list 'loop/*'   # ветки прогонов: в них работа
```
