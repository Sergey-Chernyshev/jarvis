# Удалённые агенты: Claude Code и Codex на другой машине

Агент работает на VPS (или на рабочей станции в офисе), а видно и слышно его
здесь — в общем списке сессий, с тостами, голосом и ответом прямо из панели.

Дизайн фичи: [`superpowers/specs/2026-08-05-remote-agents-design.md`](superpowers/specs/2026-08-05-remote-agents-design.md).
Крейт узла: [`../src-tauri/node/README.md`](../src-tauri/node/README.md).

## Зачем это

Ноут закрывается, спит и переезжает между сетями — а ночной прогон на VPS в это
время работает и, вполне возможно, уже полчаса стоит на вопросе о разрешении.
Держать всё на ноутбуке — значит держать ноутбук открытым.

Просто «ходить по SSH и смотреть» не годится: пока ноут спал, события никто не
собрал, и по возвращении ты видишь только текущее состояние — без того, что
происходило ночью. Поэтому на удалённой машине живёт **узел** (`jarvis-node`):
он принимает хуки агентов локально и **копит события в кольцевом буфере**, а
ноут, проснувшись, забирает всё пропущенное с того места, где остановился.

## Как это устроено

```
ноут (Jarvis)                                  VPS
─────────────                                  ───
демон                                          jarvis-node
  ├─ ssh -N -L 127.0.0.1:PORT:~/.jarvis/node.sock ──▶ unix-сокет 0600
  │      (поднимает и держит сам Jarvis)              │
  ├─ GET /events?since=<курсор>  ◀── кольцевой буфер ─┤
  ├─ GET /file?path=&from=       ◀── кусок транскрипта┤
  └─ POST /reply · /control      ──▶ tmux -L jarvis ──┘
                                          ▲
                          claude / codex ─┘ (хуки → jarvis-hook → node.sock)
```

Разделение труда простое: **узел ничего не понимает**. Он не ведёт реестр, не
считает статусы, не парсит транскрипты, не уведомляет. Он принимает конверты от
`jarvis-hook`, складывает их в буфер с монотонным курсором и умеет три вещи
наружу: отдать события, отдать кусок файла транскрипта, вставить текст в tmux.
Всю интерпретацию делает ноут — тем же кодом, что и для локальных сессий:
событие с VPS проходит через тот же редьюсер, только с меткой источника.

Отсюда следствия, которые полезно держать в голове:

* удалённая сессия ведёт себя как локальная — те же статусы, тосты, голос, чат,
  доска задач, `/`-команды;
* идентификаторы сессий с разных машин не обязаны различаться, поэтому ключ
  реестра — `<имя узла>:<id>`, а в списке у строки появляется бейдж с именем узла;
* пока ноут спит, узел копит события, но **не уведомляет**: некому.

## Что нужно на той машине

| нужно | зачем | если нет |
| --- | --- | --- |
| SSH-доступ по ключу | единственный транспорт | установка откажется работать |
| `curl` | им `jarvis-hook` отправляет события в узел, им же качается сам узел | узел не получит **ничего** |
| `tmux` | ответ в сессию и пульт (`tmux -L jarvis`) | статусы и уведомления работают, ответ нет |
| `claude` и/или `codex` | собственно агенты | ставь позже: хуки уже будут ждать |
| `systemd --user` | автозапуск узла | узел придётся поднимать руками (`@reboot` в cron) |

Аутентификация — твоя обычная SSH: ключи, `~/.ssh/config`, агент-форвардинг.
Jarvis не заводит собственных секретов, ничего не спрашивает и ничего не хранит.
Если ходишь на машину под алиасом (`Host vps` в `~/.ssh/config`) — передавай
установщику именно алиас: Jarvis зовёт тот же `ssh` и видит тот же конфиг.

## Установка

### Из панели (обычный путь)

Настройки → **Удалённые** → «Новый узел». Нужен только ssh-хост.

1. **Проверить машину.** Jarvis сходит туда по ssh и покажет, что нашёл: ОС и
   архитектуру, есть ли `tmux`, `curl`, агенты и `systemd --user`, и откуда
   возьмётся сам узел. Это разведка — ничего ещё не меняется.
2. **Установить.** Ход установки виден по шагам: узел, шим, хуки агентов,
   автозапуск, проверка. Занимает от десятков секунд до пары минут.
3. Узел появляется в списке и сразу начинает работать — перезапускать панель
   не нужно.

Если ssh не пустил, панель покажет причину и предложит **публичный ключ этой
машины**: скопируй его в `~/.ssh/authorized_keys` на той стороне (или вставь в
панель хостера при создании сервера). Ключа нет вовсе — там же кнопка завести
`ed25519`. Свои ключи Jarvis не создаёт молча и чужие не трогает.

### Из терминала

То же самое одной командой — если панель не открыта или узлов много:

```bash
jarvis-setup remote add <имя> <ssh-хост> [--dir <путь>]
```

```bash
# алиас из ~/.ssh/config
jarvis-setup remote add vps vps-work
# или как в ssh
jarvis-setup remote add vps dev@203.0.113.10
# каталог Jarvis на той стороне, если не ~/.jarvis
jarvis-setup remote add vps vps-work --dir /srv/jarvis
```

`<имя>` — как узел будет называться в списке сессий; оно же становится
префиксом идентификаторов и именем файла курсора, поэтому только латиница,
цифры и `.`, `-`, `_`.

### Бинарь узла

`jarvis-node` — обычный бинарь, и он должен быть собран **под ту машину**:
mac-сборка на Linux-VPS не запустится. Установщик это проверяет по заголовку
файла и отказывается заливать заведомо чужой формат, а после заливки ещё и
запускает `--version` на той стороне — обрезанная закачка и сборка не под тот
таргет выглядят одинаково безобидно ровно до первого запуска.

Откуда он берётся, по порядку:

1. **Готовый файл на этой машине** — если он есть и годится для той стороны.
   Ищется в `$JARVIS_NODE_BIN`, рядом с `jarvis-setup`, в
   `src-tauri/target/release/` и `src-tauri/target/<триплет>/release/`.
   Обычно это дорога разработчика.
2. **Скачивание на самой VPS** из релиза той же версии — основной путь для
   установленного приложения: у него нет ни исходников, ни линкера под Linux.
   Требует `curl`, который там и так нужен хукам.
3. **Сборка на той машине** из исходников, вшитых в приложение, — если там
   есть `cargo`. Крейт крошечный (три зависимости), но первый раз это пара
   минут: cargo тянет их с crates.io.

Собрать вручную, если хочется управлять этим самому:

```bash
# на самой VPS, из копии репозитория
cd src-tauri && cargo build --release -p jarvis-node

# или кросс-сборкой с ноутбука (нужен линкер под цель)
cd src-tauri && cargo build --release -p jarvis-node --target x86_64-unknown-linux-gnu

# и указать файл явно
JARVIS_NODE_BIN=/путь/к/jarvis-node jarvis-setup remote add vps vps-work
```

Узел — отдельный пакет именно ради этого: внутри `src-tauri` он тянул бы за
собой Tauri и не собрался бы на голой Linux-машине (подробности —
[`../src-tauri/node/README.md`](../src-tauri/node/README.md)).

### Что команда делает на той стороне

1. **Проверяет связь** (`ssh -o BatchMode=yes <host> true`) и заодно снимает
   слепок машины: `$HOME`, ОС, архитектура, наличие `tmux`, `curl`, агентов и
   `systemd --user`. Всё, кроме связи, — предупреждения, а не отказ.
2. **Заливает узел** в `<dir>/bin/jarvis-node` (0755) — через `ssh 'cat > tmp && mv'`,
   чтобы работающий узел спокойно пережил обновление.
3. **Заливает шим** `<dir>/bin/jarvis-hook` — тот же, что локально, но
   стучащийся в `node.sock` (а не в `run.sock` демона).
4. **Прописывает хуки агентов** — `~/.claude/settings.json` всегда,
   `~/.codex/hooks.json` если там есть Codex. Форма записей ровно та же, что у
   локальной установки: merge, а не overwrite (чужие хуки остаются на месте),
   бэкап перед правкой, идемпотентно.
5. **Настраивает автозапуск**: `~/.config/systemd/user/jarvis-node.service`,
   `Restart=always`, плюс `loginctl enable-linger` — без него менеджер
   пользователя гаснет с последней ssh-сессией и уносит узел с собой. Если
   `systemd --user` недоступен, команда честно об этом говорит и показывает
   ручной путь (`nohup …` сейчас, `@reboot` в `crontab -e` — на будущее).
6. **Проверяет результат**: узел ответил своей версией, сокет открыт.
7. **Дописывает узел в настройки** ноутбука (`~/.jarvis/settings.json`, ключ
   `remotes`) и печатает готовую строку — на случай, если файл придётся править
   руками.

Команда идемпотентна: повторный запуск обновляет бинарь, перезапускает юнит и
правит ту же запись в настройках, а не заводит второй узел.

> Если панель Jarvis была открыта во время установки — перезапусти её: настройки
> живут в её кэше, и она перезапишет файл своей копией.

### Как запускать сессии на той машине

Шим `claude`/`codex` и PATH-блок на удалённую машину **не ставятся** — там нет
ни панели, ни терминала, а править чужой `~/.bashrc` установщик не должен.
Поэтому tmux-обёртку заводишь сам:

```bash
ssh vps-work
tmux -L jarvis new -s work     # тот же отдельный сервер, что и локально
claude                          # или codex
```

Сервер именно `-L jarvis`: узел вставляет ответы только в него. Агент,
запущенный вне tmux, будет виден и слышен (события шлёт хук, а не tmux), но
ответить в него и переключить модель из панели не получится — ровно как у
локальной сессии «вне tmux».

Отключаться можно как обычно (`Ctrl-b d` или просто закрыть ssh): агент живёт
дальше, узел продолжает копить события.

### Ручной путь

Установщик ничего волшебного не делает, и всё то же можно сделать руками:
собрать `jarvis-node`, положить его в `~/.jarvis/bin/`, скопировать туда же
`bin/jarvis-hook` (заменив в нём `run.sock` на `node.sock`), прописать хуки той
же формы, запустить узел и добавить `{"name": …, "sshHost": …, "jarvisDir": …}`
в `remotes` файла `~/.jarvis/settings.json` — либо через вкладку «Удалённые».

## Как это выглядит в интерфейсе

**Настройки → «Удалённые»** — список узлов: имя, ssh-хост, каталог, точка
состояния («на связи» / «не отвечает» / «не проверен») и кнопки «Проверить» и
«Удалить». Там же форма добавления узла, если он уже стоит на той машине.

**Список сессий** — удалённые сессии стоят в общем списке с бейджем-именем узла;
всё остальное как у локальных: статус, ветка, модель, доска задач, чат, ответ и
пульт.

## Диагностика

Первым делом — командная проверка узла:

```bash
jarvis-setup remote status vps
```

Она показывает по ssh: жив ли процесс, есть ли сокет, что отвечает
`jarvis-node --version`, в каком состоянии юнит и сколько живых пан в
`tmux -L jarvis`.

Второе место — лог ноутбука: `~/.jarvis/jarvis.log`, строки с префиксом
`[remote]` (подъём туннеля, версия узла на рукопожатии, «связи нет — …», gap).

| симптом | что смотреть |
| --- | --- |
| «не отвечает» сразу после установки | `ssh <host> true` — ключи/known_hosts; `remote status` — поднялся ли узел |
| узел жив, событий нет | стоит ли на той машине `curl`; есть ли хуки в `~/.claude/settings.json`; **перезапущены ли сессии** — хуки берутся снапшотом на старте сессии |
| туннель постоянно переподнимается | в логе будет строка ssh с причиной: `Permission denied`, `Host key verification failed`, `no such file` (нет сокета — узел не запущен) |
| «связи нет» после сна ноутбука | это норма: ssh-соединение рвётся молча, `ServerAlive*` превращает его в честный выход, следующий круг поднимает туннель заново (пауза растёт 1, 2, 4, 8, 16, 30 с) |
| в панели дырка в истории | узел отдал `gap`: буфер переполнился, пока ноут спал. Ноут перечитывает транскрипты целиком — часть событий (например, тосты) за это время просто не случилась. Лечится ёмкостью: `JARVIS_NODE_BUFFER` в юните |
| ответ не вставляется | сессия запущена вне `tmux -L jarvis` (или tmux на VPS не установлен) — см. «Как запускать сессии» |
| события идут дважды после перезапуска ноута | так и задумано: курсор двигается **после** выдачи событий наружу, дубль редьюсер переживает, пропажу — нет |

Полезные команды на той стороне:

```bash
systemctl --user status jarvis-node.service
journalctl --user -u jarvis-node.service -n 100 --no-pager
ls -l ~/.jarvis/node.sock                 # должен быть srw------- (0600)
curl -s --unix-socket ~/.jarvis/node.sock http://node/hello   # версия, uptime, буфер
```

### Курсор

Ноут помнит, докуда дочитал ленту узла: `~/.jarvis/remotes/<имя>.cursor`.
Файл переживает перезапуск — иначе после каждого старта Jarvis перечитывал бы
весь буфер (дубли) или, наоборот, терял хвост. Удалить его безопасно: узел
отдаст всё, что есть в буфере, и сам объявит `gap`, если начало уже вытеснено.
Откат курсора назад (узел перезапустился и начал нумерацию заново) ноут
распознаёт и тоже считает потерей — молча «не заметить» рестарт было бы худшим
из вариантов.

## Безопасность

* **Наружу узел не слушает ничего.** Единственный вход — unix-сокет
  `<dir>/node.sock` с правами `0600` в каталоге `0700`; TCP-порт не
  открывается ни на одном интерфейсе.
* **Транспорт — SSH и только SSH.** Ноут пробрасывает `ssh -N -L 127.0.0.1:<порт>:<сокет>`,
  то есть локальный порт петли на удалённый сокет. Порт слушается на `127.0.0.1`
  и выбирается свободный при каждом подъёме.
* **Своих секретов нет.** Ни токенов, ни паролей, ни ключей Jarvis не заводит и
  на диск не пишет — аутентификация целиком твоя ssh-шная. Пароль установщик не
  спросит: `BatchMode=yes`, и чужой отпечаток хоста молча не принимается.
* **Узел — не файловый сервер.** `/file` отдаёт только то, что лежит под корнями
  транскриптов (`~/.claude`, `$CODEX_HOME`): путь канонизируется и проверяется
  на префикс, поэтому ни `..`, ни симлинк из разрешённого каталога наружу не
  выводят, а каталоги не листаются вовсе.
* **Ввод уходит argv, а не строкой шелла.** Текст ответа доезжает до
  `tmux set-buffer` элементом argv — интерполяции в команду нет.
* **Аутентификации на самом узле нет и не должно быть.** Кто добрался до сокета
  через SSH-туннель — тот уже владелец учётки на той машине; второй замок на той
  же двери ничего не добавил бы.

Что это значит на практике: доступ к удалённым сессиям ровно такой же, как
доступ по SSH к той машине. Забрал ключ — забрал всё.

## Ограничения

* **Узлу нужен tmux** на удалённой машине — без него ответ в сессию невозможен
  там же, где и локально.
* **Пока ноут спит, никто не уведомляет.** Узел копит события; тосты и голос
  случаются на ноутбуке, когда он вернётся.
* **Буфер конечен** (по умолчанию 2000 событий). Переполнение отдаётся честно
  (`gap`), но события, потерянные в дырке, не восстанавливаются — восстанавливается
  только состояние сессий, из транскриптов.
* **Голос, диктовка, «не спать» и клавиши — локальные.** Удалённой машины они не
  касаются.
* **Хуки берутся снапшотом на старте сессии**: сессии, запущенные до установки
  узла, событий слать не начнут — перезапусти их.
* **Автозапуск — только systemd --user.** Своего супервизора Jarvis не
  изобретает; на машине без systemd узел поднимается вручную или из cron.
* **Узел не проверяет, кто пришёл**, и не шифрует ничего сам — обе задачи целиком
  на SSH.
