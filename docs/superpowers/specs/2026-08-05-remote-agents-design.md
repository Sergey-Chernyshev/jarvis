# Удалённые агенты: узел на VPS

**Дата:** 2026-08-05

Подключение к Claude Code / Codex, запущенным на другой машине (VPS, рабочая
станция) — так, чтобы они были в общем реестре, слали уведомления и принимали
ответы, как локальные.

## Почему узел, а не «просто SSH»

Ноут спит и закрывается, а агент на VPS в это время работает и, возможно,
упирается в вопрос. Тянуть события поллингом с ноута — значит терять всё, что
случилось, пока его не было. Поэтому на VPS живёт **узел**, который принимает
хуки локально и **копит события в кольцевом буфере**; ноут, проснувшись,
забирает всё пропущенное с курсора.

## Чего узел НЕ делает

Узел — не второй Jarvis. На VPS не нужны ни панель, ни голос, ни уведомления:
человек сидит за ноутом. Поэтому узел **не** тащит Tauri и **не** переиспользует
`Daemon` (тот сцеплен с `AppHandle` в 74 местах — headless-режим означал бы
рефактор всего ядра). Узел — тонкий транспорт:

| умеет | не умеет |
| --- | --- |
| принимать хуки в свой unix-сокет | вести реестр и статусы |
| копить события с курсором | парсить транскрипты |
| отдавать кусок файла транскрипта | уведомлять, озвучивать |
| выполнять `tmux send-keys` | UI |

Всю интерпретацию — статусы, ходы, сводки — делает ноут своим существующим
кодом. Событие с VPS проходит через тот же `apply_event`, что и локальное,
только с меткой источника.

## Транспорт: SSH

Узел слушает **только unix-сокет** (0600) и не открывает ни одного порта
наружу. Ноут ходит к нему через `ssh -L`, пробрасывая локальный порт на
удалённый сокет. Отсюда: аутентификация — твоя обычная SSH (ключи, `~/.ssh/config`,
агент-форвардинг), новых секретов Jarvis не заводит и на диск не пишет.

```
ноут                                   VPS
────                                   ───
Jarvis ──ssh -L 127.0.0.1:PORT:~/.jarvis/node.sock──▶ jarvis-node
                                            ▲
                                            └── jarvis-hook (claude/codex)
```

## Протокол узла

Минимальный HTTP поверх сокета — тем же axum, что и у демона.

| метод | зачем |
| --- | --- |
| `GET /hello` | версия узла, имя хоста, uptime — для проверки связи |
| `GET /events?since=<cursor>` | события с курсора; long-poll до 25с |
| `GET /file?path=<p>&from=<off>` | кусок транскрипта (только из `~/.claude`/`~/.codex`) |
| `POST /reply` | `{pane, text}` → `tmux -L jarvis` вставка |
| `POST /control` | `{pane, cmd}` → слэш-команда в пану (модель/effort) |
| `POST /keys` | `{pane, keys}` → план клавиш в пикер вопроса |
| `GET /panes` | живые паны `tmux -L jarvis` — узнать, что сессия ещё жива |

`/keys` появился при реализации: ответ на вопрос агента — это не вставка
текста, а последовательность клавиш, и раскладка пикеров привязана к версии
агента. Поэтому план (`[{key:"Down"},{text:"свой ответ"}]`) считает ноут своим
`answer_keys`, а узел его только проигрывает — граница «интерпретация на ноуте»
осталась ровно там же.

Курсор — монотонный `u64`. Буфер кольцевой (по умолчанию 2000 событий);
переполнение отдаётся честно: `{"gap": true}`, ноут перечитывает транскрипты
целиком, а не делает вид, что ничего не потерял.

`/file` жёстко ограничен корнями транскриптов: путь канонизируется и
проверяется на префикс, `..` не проходит. Узел не файловый сервер.

## Что меняется на ноуте

* `Session.remote: Option<String>` — имя удалённого узла; `None` = локальная.
* Идентификаторы сессий пространство имён не делят: ключ реестра становится
  `<remote>:<id>`, чтобы id с разных машин не столкнулись.
* Действия (ответ, пульт, ответ на вопрос, чтение транскрипта) маршрутизируются:
  локальная — как сейчас, удалённая — в свой узел (`tmux::Target`).
* Настройки: список узлов (`имя`, `ssh host`, `каталог jarvis`).
* Всё, что раньше читало транскрипт из файловой системы, ходит через
  `Daemon::transcript_text` — она сама решает, файл это или запрос к узлу.
  Это касается меты, сводок ходов, финального ответа и `chats.read`.

### Что нельзя судить по локальной машине

Реализация вскрыла класс ошибок, которого в дизайне не было: **pid и номер
паны уникальны только в пределах машины**. Локально `%3` — это одна пана, на
VPS `%3` — совсем другая, и pid 4242 там принадлежит чужому процессу. Поэтому:

* живость удалённой сессии определяется по `/panes` её узла, а не по
  локальной таблице процессов;
* выселение призраков (`evict_pane`) сравнивает пану **вместе с машиной** —
  иначе событие с узла выселяло бы живую локальную сессию с тем же номером;
* локальные резолверы (имя tmux-сессии, GUI-приложение-владелец, ветка из
  `.git` по cwd) для удалённых сессий не запускаются: в лучшем случае они
  промахнутся, в худшем — уверенно соврут про чужой объект с тем же именем.

## Установка узла

`jarvis-setup remote add <name> <ssh-host>` — кладёт узел на ту сторону, ставит
там хуки и автозапуск, прописывает узел в настройки. Ручной путь (собрать
самому и скопировать) остаётся.

То же самое доступно **из панели**: разведка машины (`remotes_preflight`)
показывает, что там есть, до того как что-то менять, а сама установка
(`remotes_install`) едет событиями шагов — она занимает минуты и блокировать
на ней панель нельзя.

### Откуда берётся бинарь

Дизайн исходил из «собери и положи», и для разработчика это верно. Для
человека с установленным `.app` — нет: у него нет ни исходников, ни линкера
под Linux. Поэтому источников три, по порядку: готовый файл на этой машине →
скачивание релиза той же версии **на самой VPS** (нужен `curl`, который там и
так обязателен для хуков) → сборка на той стороне из вшитых в приложение
исходников, если там есть `cargo`.

Все три заканчиваются одинаково — запуском `--version` на той машине. Чужая
архитектура, обрезанная закачка и сборка не под тот таргет выглядят одинаково
безобидно ровно до первого запуска, и ловить их надо здесь, а не в логе
systemd.

## Границы

* Узел требует на VPS **tmux** — без него ответ в сессию невозможен там же,
  где и локально.
* Пока ноут спит, узел копит события, но не уведомляет: некому.
* Голос, диктовка и «не спать» остаются локальными — удалённой машины они
  не касаются.
* Вьюер документов (`file_read` / дифф) для удалённых сессий не работает и
  честно об этом говорит: узел отдаёт только транскрипты, файловым сервером
  он сознательно не является.
* Терминал удалённой сессии не сфокусировать и не пингануть оверлеем — он
  на другой машине, и оба действия отказывают с внятным текстом.
* После потери событий (`gap`) перечитывается мета сессий узла; статус, если
  он застрял, чинит обычная 30-секундная сверка живости.
