## 1. Зачем

Десктоп вырос до ~52k строк Rust и ~14k строк JS. Каждая новая способность —
голос, диктовка, wake-word, циклы, пайплайны, изменения, удалённые агенты —
добавлялась одинаково: модуль в `src-tauri/src/`, поле в `Daemon`, пачка
`#[tauri::command]` в `ipc.rs` (сейчас их больше 100), вкладка-хардкод в
`NAV`/`RENDERERS` (`ui/settings2.js`, 2862 строки), ветка в `match` трея и в
меню голосовых скилов. Стоимость каждой следующей способности растёт, потому
что она пришивается к ядру в четырёх местах, а не подключается к нему в одном.

При этом **швы для другой модели уже прорезаны и работают**:

- `capability/` — реестр именованных возможностей, гейт с классами риска,
  подтверждениями и аудитом, гранты потребителей (`panel`/`agent`/`plugin`),
  токены в `~/.jarvis/tokens.json`;
- `entities.rs` — реестр сущностей ядра (HA-модель) + капабилити
  `entities.publish` / `entities.query`;
- `settings.rs` — блоки `plugins.<id>` с готовыми аксессорами;
- `power/mod.rs` — фактически хост из двух захардкоженных плагинов: тумблер
  `_enable`, `plugins_status`, `plugins_cmd`, декларативный `tray_items()`.

Не хватает ровно одного: **ядра, которое умеет держать плагины** — и того, что
из этого следует: наши собственные способности становятся такими же плагинами,
как чужие. Отсюда цель.

**Цель.** Десктопный Jarvis = **ядро (kernel)** + **набор плагинов**. Ядро не
знает ни про «Не спать», ни про голос, ни про VM — оно знает про жизненный цикл
плагина, про capability-гейт, про сущности, про вклады (contributions) в UI/трей/
скилы и про то, как всё это показать пользователю. Способности живут в плагинах,
first-party и сторонних, **на одном и том же контракте**.

**Не цель** (сознательно вне рамок): переписать 52k строк; поменять UX; вынести
голос/STT в отдельные процессы; магазин плагинов и подпись; UI-плагины с
произвольным HTML.

## 2. Что «плагин» значит здесь

Плагин — это **манифест + рантайм**.

- **Манифест** — данные (JSON или Rust-константа): кто я, что мне нужно, что я
  даю. Из него ядро само строит UI настроек, пункты трея, меню голосовых скилов,
  грант потребителя и права на данные других плагинов. Ядро **не** содержит
  кода, специфичного для конкретного плагина.
- **Рантайм** — то, что исполняет команды: либо код в процессе Jarvis, либо
  отдельный процесс.

### 2.1 Два рантайма, один контракт

| | **Builtin** (in-process) | **External** (сайдкар-процесс) |
|---|---|---|
| Кто | first-party способности Jarvis | сторонние интеграции, тяжёлые/нативные |
| Форма | Rust-тип, реализующий трейт `Plugin` | любой исполняемый файл |
| Манифест | константа в коде | `manifest.json` рядом с бинарём |
| Канал | прямой вызов | JSON-lines по stdin/stdout |
| Доступ к ядру | напрямую (`Arc<Daemon>`) | `capability::invoke` через гейт |
| Изоляция | нет (наш код, наше доверие) | процесс; крэш не роняет Jarvis |
| Цена | ноль | ~1 процесс, ~1 handshake |

Разделение честное, а не идеологическое. Голос держит аудио-устройство и
разделяет `AudioHub` с диктовкой; wake-word крутит ONNX в общем аудио-веере.
Выносить это в процесс ради чистоты — заплатить задержкой и сложностью за
свойство, которое нам не нужно: **мы своему коду доверяем**. Что нам нужно от
плагинности своего кода — это единый жизненный цикл, декларативные настройки,
одна точка регистрации и отсутствие хардкода в четырёх местах. Это даёт builtin.

Что **не** даёт builtin и о чём нельзя врать в UI: builtin-плагин не изолирован.
Выключенный builtin — это «не держит ресурс и не отвечает на команды», а не
«выгружен из процесса». Ровно так это уже работает у `keep-awake` (см. коммент в
`power/mod.rs::init`), и ровно так это должно быть написано в разделе «Плагины».

### 2.2 Инвариант ядра

> **INV-KERNEL.** В ядре нет ветвлений по идентификатору плагина. Ни `match id`,
> ни `if id == "…"`, ни списка имён в UI. Всё, что ядро делает с конкретным
> плагином, оно делает по данным его манифеста и через его рантайм.

Это тестируемо (§8) и это единственная защита от того, что «плагинность» тихо
выродится обратно в хардкод.

## 3. Ядро: что остаётся

Ядро — это то, что не является ничьей способностью:

1. **Хост плагинов** (`plugin/`): discovery, валидация манифеста, enable/disable,
   выпуск/отзыв токена, spawn/handshake/supervise сайдкаров, статусы.
2. **Capability-платформа** (`capability/`): реестр, гейт, гранты, аудит,
   токены — **уже есть**, не трогаем, только дополняем регистрацией капабилити
   от плагинов.
3. **Реестр сущностей** (`entities.rs`) — **уже есть**; это шина данных между
   плагинами.
4. **Шелл UI**: панель, окно настроек, тосты, трей — рамы, в которые плагины
   кладут вклады. Ядро владеет треем и тостами; плагин их только просит.
5. **Сессии агентов** — данные, вокруг которых всё вертится. Остаются в ядре:
   это не способность, а предметная модель Jarvis (как `hass.states` у Home
   Assistant). Плагины читают их капабилити `sessions.*` и дополняют через
   `sessions.ingest`.

Всё остальное со временем уезжает в плагины. Порядок переезда — §9.

## 4. Контракт плагина

### 4.1 Манифест

Одна форма для обоих рантаймов (у builtin — та же структура, собранная в коде):

```jsonc
{
  "id": "keep-awake",              // [a-z0-9-], уникален, = ключ в settings.plugins
  "name": "Не спать",
  "version": "1.0.0",
  "description": "Не даёт маку уснуть, пока агенты работают",
  "icon": "coffee",                // имя из набора иконок UI (не файл плагина)
  "kind": "builtin" | "external",
  "entry": { "path": "bin/plugin" },   // только external, относительно папки плагина
  "capabilities": ["read", "control"], // классы риска → Consumer::plugin(id, classes)
  "uses": ["notify.toast", "sessions.list"],  // least-privilege внутри классов
  "provides": [{ "kind": "vm", "attrs": ["state"] }],
  "consumes": [{ "plugin": "agent-vm", "kind": "vm" }],
  "settings": [ /* схема → автогенерация UI, §4.2 */ ],
  "commands": [ /* что умеет рантайм, §4.3 */ ],
  "tray": true,
  "skills": [ /* голосовые скилы, §4.5 */ ]
}
```

Правила валидации (отказ = плагин виден со статусом `error`, но не грузится):
`id` в нижнем регистре без точек; `version` — semver; `kind` известен;
`capabilities` без `admin` (фильтруется молча — так уже делает
`Consumer::plugin`); `settings[].key` уникальны; `entry` обязателен и только
для `external`; неизвестные поля игнорируются (forward-compat).

### 4.2 Схема настроек

Типы — ровно те компоненты, что уже есть в `ui/settings2.js`
(`toggle`, `segmented`, `number`, `text`, `select`), плюс `title`/`hint`/
`default`/`depends` (показывать поле только если другое поле истинно). Значения
живут в `settings.plugins.<id>` — аксессоры `plugin()` / `set_plugin()` есть.

Ключи `enabled` — зарезервирован ядром (тумблер плагина), плагин его в схеме не
объявляет.

### 4.3 Команды рантайма

`commands[]` — то, что ядро может позвать у плагина: `{ name, title?, args? }`.
Ядро зовёт их из UI (кнопка в детали плагина), из трея и из скилов. Плагин
отвечает `{ ok, value? , error? }`.

Зарезервированные имена ядра (плагин их не объявляет и не обрабатывает):
`_enable`, `_status`, `_tray`. Первое ядро исполняет само (тумблер + жизненный
цикл), два других — опрашивает у рантайма.

### 4.4 Вклады в трей

Плагин отдаёт на `_tray` тот же декларативный список, что сейчас строит
`power::tray_items()` (`Label` / `Action` / `Check` / `Submenu` / `Separator`).
Ядро склеивает секции всех включённых плагинов в порядке их регистрации и
маршрутизирует клик обратно владельцу по префиксу `id` — **без `match` по имени
плагина** (сейчас в `tray.rs` он есть; переезд — инкремент 4).

### 4.5 Голосовые скилы

`skills[]` = `{ name, description, risk, args }`. `description` попадает в меню
LLM-планировщика, `risk` — в класс гейта, вызов — команда рантайма. Это снимает
хардкод-триплет в `convo/skills.rs` (`skills_menu()` + `match` в `dispatch()` +
спец-кейсы). Переезд — инкремент 6.

## 5. Протокол сайдкара

Один дуплексный канал: **JSON-lines по stdin/stdout** дочернего процесса.
Почему не UDS, как в спеке от 2026-07-03: канал ядро→плагин там был описан как
`POST /plugin/skill`, что требует от плагина поднимать сервер, а от ядра —
знать его адрес; long-poll `/plugin/events` добавляет третью полусвязь. Труба
даёт то же самое даром и, главное, **идентичность по построению**: сообщение из
stdout — от этого процесса, подделать её нечем, токен для этого канала не
нужен.

Формат кадра — одна строка JSON:

```
→ {"id":1,"method":"_status","params":{}}          ядро → плагин
← {"id":1,"ok":true,"value":{...}}                 плагин → ядро
← {"id":1,"ok":false,"error":"…"}
← {"event":"entities","data":{...}}                плагин → ядро, без ответа
```

- **Handshake.** Первый кадр от плагина — `{"event":"register","data":
  {"protocol":1,"pid":…}}`. До него плагин не считается живым; таймаут 5с →
  статус `error`. Несовпадение мажора протокола → `incompatible`, не грузим.
- **Окружение процесса**: `JARVIS_SOCKET`, `JARVIS_PLUGIN_ID`, `JARVIS_TOKEN`.
  Труба — для управления; **вызовы капабилити идут по UDS с токеном**, потому
  что там уже стоит гейт с грантами, подтверждениями и аудитом, и второй путь в
  ядро строить нельзя.
- **Таймауты**: команда — 10с (скилы — по спеке voice), `_status`/`_tray` — 2с;
  просрочка = ошибка команды, не смерть плагина.
- **Надзор**: крэш → рестарт с экспоненциальным backoff (1с → 60с, сброс после
  60с жизни); 5 падений подряд → `error` и стоп (без бесконечного цикла).
  `disable` → SIGTERM, через 3с SIGKILL, отзыв токена.
- **stderr** плагина — в `~/.jarvis/jarvis.log` с префиксом `[plugin:<id>]`.

## 6. Безопасность

Модель угроз не меняется (см. capability-спеку v2 §3): однопользовательская
машина, сокет `0600`, реальное сдерживание — подтверждения на side-effect'ы, а
не токен.

Что добавляет плагинное ядро:

- **External-плагин — недоверенный код**: грант `Consumer::plugin` (least-
  privilege из манифеста, `admin` отфильтрован, confirm на каждый side-effect,
  анти-эскалация `SECURITY_KEYS`/`SETTINGS_ALLOWLIST`) — **уже реализовано и
  покрыто тестами**. Токен выдаётся при enable, отзывается при disable.
- **Builtin-плагин — доверенный код**: зовёт сервисы напрямую, гранта не
  получает, токена не имеет. В UI это должно быть видно (бейдж «встроенный»),
  чтобы список «Плагины» не создавал ложного впечатления, будто наши
  способности песочены.
- **Установка external в v1 — только вручную** (папка `~/.jarvis/plugins/<id>/`)
  и first-party из репо (`plugins/<id>/`). Ни магазина, ни подписи, ни
  авто-обновления: их отсутствие — принятое ограничение, а не недоделка.
- Манифест — **декларация желаний, а не прав**: он говорит, чего плагин просит;
  права выдаёт пользователь тумблером, а гейт сверяет каждый вызов.

## 7. Что происходит с UI

Одна новая вкладка «Плагины» в `NAV`, один рендерер, дальше всё data-driven:

- **Список**: иконка, имя, версия, бейдж рантайма (встроенный / внешний),
  статус (`running` / `stopped` / `error` / `incompatible`), тумблер.
- **Деталь**: настройки из схемы манифеста существующими компонентами; блок
  «Права» (классы + `uses` + гранты на `consumes`, по умолчанию выключены);
  блок «Здоровье» (pid, аптайм, последняя ошибка, «Перезапустить»); кнопки
  команд из `commands[]`.
- HTML от плагина не рендерится (v1). Не хватило схемы — расширяем схему.

Существующие вкладки при этом никуда не деваются: переезд способности в плагин
**не обязан** утаскивать её настройки в общую вкладку «Плагины». Манифест может
объявить `"pane": "awake"` — «мои настройки живут в такой-то существующей
вкладке». Так «Бодрость» остаётся «Бодростью», а плагинность — под капотом.

## 8. Тесты

- **Манифест**: валидация (хороший/битый id, отсутствующий entry у external,
  дубли ключей настроек, `admin` в capabilities отфильтрован).
- **Хост**: enable → токен появился в `tokens.json`; disable → исчез; builtin
  токена не получает; статусы; рестарт с backoff; неизвестная команда → ошибка,
  не паника.
- **Сайдкар**: фейк-плагин (скрипт) — handshake, ответ на `_status`, таймаут,
  крэш → рестарт, несовместимый протокол → `incompatible`.
- **INV-KERNEL** (§2.2): тест-грепом по `src-tauri/src/plugin/` и `ui/` — в
  ядре нет ветвлений по id конкретных плагинов из реестра.
- **Регресс**: `plugins_status` / `plugins_cmd` сохраняют форму ответа, панель
  «Бодрость» продолжает работать после переезда `keep-awake`/`clamshell`.

## 9. Инкременты

Каждый — отдельный коммит с тестами, ядро остаётся рабочим на каждом шаге.

1. ✅ **Ядро хоста**: `plugin/{manifest,contract,host,builtin}.rs` — манифест,
   трейт `Plugin`, реестр, enable/disable, токены, статусы.
2. ✅ **Сайдкар-рантайм**: JSON-lines, handshake, таймауты, надзор, discovery
   `~/.jarvis/plugins/*/manifest.json`; фейк-плагины в тестах; референсный
   плагин `plugins/example-hello/` (он же проверяется тестом — пример в
   документации обязан работать).
3. ✅ **Вкладка «Плагины»**: generic-рендерер по манифесту, тумблеры, права,
   здоровье, команды; `plugins_status`/`plugins_cmd`/`plugin_set` — у хоста.
4. ✅ **Переезд `keep-awake` и `clamshell`** в builtin-плагины: `power/mod.rs`
   потерял роль хоста (−366 строк) и стал двумя плагинами; трей маршрутизирует
   по владельцу, таблицы «что значит эта кнопка» в ядре больше нет.
   INV-KERNEL закреплён тестом `kernel_never_branches_on_a_plugin_id`.
5. **Переезд `voice` и `wakeword`** — самые «фичевые» способности с большими
   блоками настроек; проверяют, что `"pane"` (§7) работает и вкладки не
   разъезжаются.
6. **`SkillRegistry`**: голосовые скилы из манифестов, конец хардкод-триплета.
7. **External-плагин живьём**: `agent-vm` по спеке от 2026-07-03 — первый
   сторонний потребитель контракта, он же проверка, что контракт не выродился
   под нужды builtin.

Инкременты 1–3 дают ядро; 4 доказывает модель на живой способности; 5–7 —
расширение.

## 10. Риски и честные оговорки

- **Плагинность своего кода легко имитировать.** Если builtin-плагины получат
  привилегированные хуки в ядре, «всё есть плагин» станет фикцией с лишним
  слоем. Защита — INV-KERNEL и то, что external-плагин (инкр. 7) проходит через
  тот же контракт: контракт, который держит только своих, — не контракт.
- **Переезд способности — это риск регресса без выигрыша для пользователя.**
  Поэтому порядок: сначала самые обособленные (`keep-awake`, `clamshell`), и
  каждая — отдельным коммитом с ручной проверкой живьём.
- **Схема настроек упрётся в потолок.** Часть вкладок (модели STT/TTS с
  загрузкой, рекордер хоткеев, история диктовки) схемой не выражается. Это
  ожидаемо: такие способности остаются плагинами с собственной вкладкой
  (`"pane"`), а не пытаются влезть в generic-рендерер.
- **`ipc.rs` на 100+ команд** сам по себе не рассосётся. Он уменьшится только
  вместе с переездом способностей (инкр. 4–6); ждать этого от инкрементов 1–3
  не нужно.
