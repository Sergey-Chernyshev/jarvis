# jarvis-node

Узел Jarvis на удалённой машине (VPS, рабочая станция). Принимает хуки Claude
Code / Codex в свой unix-сокет, копит их в кольцевом буфере с монотонным
курсором и отдаёт ноутбуку через SSH-туннель.

Руководство пользователя — [`docs/remote.md`](../../docs/remote.md), дизайн —
[`docs/superpowers/specs/2026-08-05-remote-agents-design.md`](../../docs/superpowers/specs/2026-08-05-remote-agents-design.md).

## Почему это отдельный пакет

Cargo резолвит зависимости на **пакет**, а не на цель: будь узел ещё одним
`[[bin]]` внутри `src-tauri`, он тянул бы за собой `tauri`, `objc2` и
`core-graphics` — и не собрался бы на голой Linux-VPS, ради которой всё и
затевалось. Поэтому у него свой `Cargo.toml` с тремя зависимостями (`axum`,
`tokio`, `serde_json`); членом воркспейса он остаётся, чтобы проверяться вместе
со всем остальным и складывать артефакты в общий `src-tauri/target`.

Вторая причина та же по духу: узел — не второй Jarvis. Ему не нужны ни панель,
ни голос, ни уведомления (человек сидит за ноутом), поэтому он не переиспользует
`Daemon` — тот сцеплен с `AppHandle` в семи десятках мест, и headless-режим
означал бы рефакторинг всего ядра. Пара десятков строк помощников
продублирована сознательно: сцепка ради них обошлась бы дороже дубля.

## Сборка

```bash
cd src-tauri && cargo build --release -p jarvis-node
# → src-tauri/target/release/jarvis-node
```

Собирать нужно **под целевую машину**: mac-сборка на Linux не запустится. Проще
всего собрать прямо на VPS из копии репозитория; кросс-сборка с ноутбука
(`--target x86_64-unknown-linux-gnu`) тоже годится, если есть линкер под цель.
Ставит узел на ту сторону команда `jarvis-setup remote add <имя> <ssh-хост>`.

## Запуск

```bash
jarvis-node            # слушать <JARVIS_DIR>/node.sock (0600)
jarvis-node --version
jarvis-node --help
```

Наружу узел не слушает ничего: единственный вход — unix-сокет с правами 0600 в
каталоге 0700, а ноут приходит через `ssh -N -L 127.0.0.1:<порт>:<сокет>`.
Аутентификация целиком ssh-шная, своих секретов узел не заводит.

По SIGTERM (штатное «стоп» от systemd) узел снимает сокет за собой — иначе
`jarvis-hook` тратил бы таймаут curl на каждое событие осиротевшего файла.

### Переменные окружения

| переменная | по умолчанию | зачем |
| --- | --- | --- |
| `JARVIS_DIR` | `~/.jarvis` | каталог данных; в нём и живёт сокет |
| `JARVIS_NODE_SOCK` | `<JARVIS_DIR>/node.sock` | путь сокета целиком (перекрывает `JARVIS_DIR`) |
| `JARVIS_NODE_BUFFER` | `2000` | ёмкость кольца событий; мусор и ноль откатываются к дефолту |
| `CODEX_HOME` | `~/.codex` | второй корень транскриптов (первый — `~/.claude`) |

Сокет называется `node.sock`, а не `run.sock`: на одной машине узел и демон
Jarvis могут стоять рядом, и делить один путь им нельзя.

## Протокол

Минимальный HTTP поверх unix-сокета — тем же axum, что и у демона.

| метод | зачем |
| --- | --- |
| `GET /hello` | версия, хост, uptime, состояние буфера — проверка связи |
| `GET /events?since=<курсор>` | события с курсора; long-poll до 25 с; при переполнении буфера — `{"gap": true}` |
| `GET /file?path=<p>&from=<off>` | кусок транскрипта; только из-под `~/.claude` / `$CODEX_HOME` |
| `POST /reply` | `{pane, text}` → вставка в `tmux -L jarvis` |
| `POST /control` | `{pane, cmd}` → слэш-команда в пану (модель/effort) |
| `POST /keys` | `{pane, keys}` → план клавиш в пикер вопроса (план считает ноут) |
| `GET /projects` | оглавление проектов машины: каталоги, сессии, время |
| `POST /launch` | `{cwd, cmd, name}` → создать каталог и поднять сессию в tmux; отдаёт пану |
| `GET /screen?pane=` | видимый экран паны — «что там на самом деле происходит» |
| `GET /panes` | живые паны `tmux -L jarvis` |
| `POST <любой другой путь>` | конверт от `jarvis-hook` (он бьёт в `/event`) |

### Транспорт

По умолчанию узел слушает ТОЛЬКО unix-сокет `<JARVIS_DIR>/node.sock` с правами
0600 и наружу не открывает ничего. Ноутбук ходит к нему через
`ssh -L порт:<сокет>`.

`JARVIS_NODE_TCP=127.0.0.1:7717` дополнительно поднимает слушатель на петле.
Установщик (`jarvis-setup remote add`, он же кнопка в панели) прописывает его
в systemd-юнит **по умолчанию** — без него мобильный клиент не подключится
вовсе, а узнать об этом можно только с телефона и уже без панели. Не нужен —
ставь с `--no-tcp`, другой порт — `--tcp=N`.
Это не про удобство: форвард на unix-сокет — расширение OpenSSH
(`direct-streamlocal`), и SSH-библиотеки под Android его почти поголовно не
умеют, а обычный TCP-форвард умеют все. Адрес обязан быть петлёй — на любом
другом узел откажется стартовать, не открыв ни одного слушателя.

Разница с сокетом одна, и её стоит знать: сокет закрыт правами 0600, а к порту
на петле может подключиться любой пользователь **той** машины. На машине, где
ты не один, оставь TCP выключенным.

Курсор монотонный и не переиспользуется даже после вытеснения: только по нему
ноут понимает, что именно он пропустил. Переполнение не заминается — честный
`gap` заставляет ноут перечитать транскрипты целиком, а не собрать дырявую
картину.

## Чего узел не делает

Не ведёт реестр и статусы, не парсит транскрипты, не уведомляет, не озвучивает,
не показывает UI. Всю интерпретацию делает ноут своим существующим кодом:
событие с VPS проходит через тот же редьюсер, что и локальное, только с меткой
источника.

Одно уточнение к «не парсит»: `/projects` читает первые килобайты свежайшего
транскрипта каждого проекта, чтобы достать `cwd`. Имя каталога Claude кодирует
необратимо (`/` и `.` превращаются в `-`, а `-` бывает и в самом имени), так
что развернуть его обратно нельзя — спросить можно только сам файл. Статусы,
ходы и сводки узел по-прежнему не считает: это по-прежнему поиск файлов, а не
понимание диалога.

## Тесты

```bash
cd src-tauri && cargo test -p jarvis-node
```

Проверяются кольцо и курсор (в том числе `gap` на вытеснении и на откате),
границы `/file` (`..`, симлинк, сосед с общим префиксом, обрыв UTF-8 на границе
куска), разбор query и аргументы вставки в tmux — последние сверяются с
`src/tmux.rs` дословно: расхождение хотя бы во флаге означало бы, что удалённая
пана ведёт себя иначе локальной.
